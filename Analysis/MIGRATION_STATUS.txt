QUESTIONS & ANSWERS
============================================================================

Q: What if DocumentTypes is empty?
A: Migration will halt in STEP 1 with clear message. Restore DocumentTypes_BACKUP or manually add entries, then rerun.

Q: What if I see constraint errors during re-enable?
A: Review the specific FK constraint name in error. Check TROUBLESHOOTING_CHECKLIST.txt for that FK. 
   Run diagnostic queries to find orphaned records. Fix them and retry constraint re-enable.

Q: Can I run this on production?
A: Yes, but after backup. The script is designed for safe execution. 
   Ensure MMGTDB2A.DocumentTypes is properly populated first. Test on development first if possible.

Q: What if ApplicationDocuments count doesn't match source?
A: Check STEP 7 output. If DocumentTypeId error occurred, that's expected. 
   Verify MMGTDB2A.DocumentTypes had valid entries. Restore backup and retry.

Q: How long does migration take?
A: Typically 2-5 minutes depending on network and server load. SQL Server operations on ~90K rows total.

Q: Will this affect other tables?
A: No. Only Users, PMICompanies, Applications, ApplicationDocuments, ApplicationReviewHistory are cleared/reloaded.
   ReviewerAvailabilities, ReviewerPerformanceMetrics, DocumentTypeAuditLogs, SystemConfigurations, etc. are untouched.
   DocumentTypes, EscalationRules, SystemConfigurations are backed up, cleared, and restored.

Q: Can I stop the script mid-execution?
A: Not recommended. Constraints will be disabled and data partially loaded. 
   If you must stop, run rollback procedure or restore backup.

Q: What about FileContent for documents?
A: Source MMGTDBCOPY doesn't have FileContent column. Migration sets it to NULL.
   Files are reconstructed from FilePath in application logic.
