MIGRATION TROUBLESHOOTING & EXECUTION CHECKLIST
===============================================

CRITICAL ISSUES ENCOUNTERED & FIXES
====================================

Issue #1: FK_DocumentTypes_Users_CreatedBy
-------------------------------------------
SYMPTOM: Error when deleting Users - "DELETE statement conflicted with REFERENCE constraint"
REASON: DocumentTypes.CreatedBy column references Users.Id
CAUSE: During target data clearing, Users was deleted before DocumentTypes entries were cleaned up
FIX: Check DocumentTypes and EscalationRules for references to Users being deleted
	 Before deleting Users, remove any rows from DocumentTypes/EscalationRules that reference old Users

Issue #2: Duplicate Primary Key on Users
------------------------------------------
SYMPTOM: Error "Violation of PRIMARY KEY constraint 'PK_Users'. Duplicate key value..."
REASON: Target MMGTDB2A already had Users from a previous incomplete migration
CAUSE: The DELETE step failed, so old Users were still in the table
FIX: Ensure DELETE FROM Users completes successfully before INSERT

Issue #3: Duplicate Primary Key on PMICompanies
-------------------------------------------------
SYMPTOM: Error "Violation of PRIMARY KEY constraint 'PK_PMICompanies'. Duplicate key value..."
REASON: Similar to Users - target had existing PMICompanies
CAUSE: DELETE step failure
FIX: Ensure DELETE FROM PMICompanies completes successfully

Issue #4: NULL DocumentTypeId
------------------------------
SYMPTOM: Error "Cannot insert the value NULL into column 'DocumentTypeId'"
REASON: DocumentTypeId is NOT NULL but source ApplicationDocuments had no mapped DocumentTypeId
CAUSE: Source MMGTDBCOPY stores document type as string (DocumentType), not as FK
FIX: 
  1. Ensure MMGTDB2A has at least one active DocumentType
  2. Use a default DocumentTypeId for all migrated docs (stored old type in LegacyDocumentType)
  3. Create mapping table if different documents should map to different DocumentTypes

Issue #5: FK_Users_PMICompanies_PMICompanyId
---------------------------------------------
SYMPTOM: Error when re-enabling constraints - FK violation
REASON: Users.PMICompanyId references PMICompanies.Id that may not exist
CAUSE: PMICompany records missing or IDs don't match
FIX: Verify all Users.PMICompanyId values exist in PMICompanies after migration

1. MMGTDBCOPY must be accessible and contain source data

4. Take backups of both databases before starting

Execution Order:

Step 1: Run MIGRATION_QUICK_FIX.sql
   - This is the corrected version addressing all issues
   - Connection: MMGTDB2A

   - Verify DocumentTypes are found and listed

   - Rerun the migration script

   - Check error message for which FK is problematic

Step 2: Post-Migration Validation
   - Run validation queries from STEP 10 of MIGRATION_QUICK_FIX.sql
   - Verify row counts match expected

Step 3: Manual DocumentType Mapping (if needed)

	 UPDATE ApplicationDocuments
	 SET DocumentTypeId = (correct DocumentTypeId)
	 WHERE LegacyDocumentType = 'somevalue'

Step 4: Connection String Update
   - Update application connection strings to point to MMGTDB2A
   - Test application connectivity and functionality

ROLLBACK PROCEDURE
==================

If migration fails catastrophically:

1. Restore MMGTDB2A from pre-migration backup

2. Or manually cleanup if backup not available:

   USE MMGTDB2A;

   -- Disable constraints
   ALTER TABLE [all tables] NOCHECK CONSTRAINT ALL;

   -- Delete migrated data (keeping reference data)
   DELETE FROM ReassignmentHistories;
   DELETE FROM AssignmentEscalations;
   DELETE FROM ApplicationAssignments;
   DELETE FROM ApplicationDocumentHistory;
   DELETE FROM ApplicationDocuments;
   DELETE FROM ApplicationReviewHistory;
   DELETE FROM Applications;
   DELETE FROM Users;
   DELETE FROM PMICompanies;
   -- Keep: DocumentTypes, EscalationRules, SystemConfigurations

   -- Re-enable constraints
   ALTER TABLE [all tables] WITH CHECK CHECK CONSTRAINT ALL;

COMMON ISSUES & QUICK FIXES
===========================

Issue: "DocumentTypeId is NULL after migration"
Fix: Ensure DocumentTypes has at least one active entry before migration
	 If needed, restore DocumentTypes_BACKUP or create a default DocumentType

Issue: "Orphaned ApplicationDocuments - no matching DocumentTypeId"
Fix: This means a row was inserted with NULL DocumentTypeId
	 Check validation query - should be zero
	 If not zero, manually update: UPDATE ApplicationDocuments SET DocumentTypeId = (valid ID) WHERE DocumentTypeId IS NULL

Issue: "Timeout during Applications insert"
Fix: Normal for 17K+ rows; increase command timeout in SQL client if needed
	 Split into smaller batches if necessary

Issue: "FK violation on Users.PMICompanyId"
Fix: Check if Users references a PMICompanyId that doesn't exist in target
	 Either create missing PMICompanies or set PMICompanyId to NULL for those Users

Issue: "Cannot re-enable FK_DocumentTypes_Users_CreatedBy"
Fix: Check if any DocumentTypes.CreatedBy references a non-existent User
	 Either delete those DocumentTypes rows or update CreatedBy to valid User
	 Restore DocumentTypes_BACKUP if needed
